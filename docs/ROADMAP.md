# Roadmap разработки торговой платформы для MOEX

**Версия документа:** 1.1  
**Дата исследования:** 8 ноября 2026 г.  
**Статусы этапов обновлены:** 10 ноября 2026 г. (синхронизация с `docs/STATUS.md`)  
**Основной стек:** TypeScript / Node.js, React, PostgreSQL  
**Брокерский API для исполнения:** T-Invest API (Т‑Банк)  
**Дополнительный источник биржевых данных:** MOEX ISS

---

## 1. Цель и границы проекта

Разработать собственную торговую платформу, которая объединяет четыре контура:

1. **Market data:** получение, нормализация и хранение исторических и текущих рыночных данных по инструментам Московской биржи.
2. **Research & analytics:** технический и статистический анализ, индикаторы, поиск рыночных ситуаций, исследование гипотез.
3. **Signals & backtesting:** формирование объяснимых сигналов, проверка торговых стратегий на истории и оценка их качества.
4. **Trading:** ручное выставление заявок из интерфейса и постепенный переход к автоматическому исполнению по утверждённым стратегиям.

Это не высокочастотный торговый терминал. Первая версия должна быть пригодна для личной систематической торговли, анализа акций и фьючерсов, тестирования стратегий и контролируемого исполнения через брокера.

### 1.1. Ключевое архитектурное решение

Необходимо разделить **биржевой источник данных** и **брокерский канал исполнения**:

- **T-Invest API** — интерфейс Т‑Банка. Через него приложение получает инструменты, котировки, свечи, стакан, сделки, портфель и отправляет брокерские поручения.
- **MOEX ISS** — информационно-статистический HTTP API Московской биржи. Он даёт структуру рынков и инструментов, свечи, сделки, котировки и исторические данные. Доступность и задержка рыночной информации зависят от подписки и условий доступа.
- **Исполнение заявок** в предлагаемой первой версии выполняется через T-Invest API. MOEX ISS не следует считать публичным API для отправки розничных заявок.

Такое разделение позволяет загружать историю из MOEX ISS, использовать брокерские realtime-потоки T‑Банка, а торговые поручения направлять через брокерский счёт. При необходимости провайдера данных или брокера можно заменить без переписывания стратегий.

> Важно: T-Invest API — API брокера, а не прямой интерфейс к торговому ядру MOEX. Для прямого биржевого подключения MOEX описывает отдельные интерфейсы, включая FAST для market data и FIX для transactional/trading задач. Это другой класс подключения, с отдельными условиями доступа и инфраструктуры, и для первой версии персонального торгового приложения он не нужен.

## 2. Что дают изученные API и SDK

### 2.1. T-Invest API

По документации T‑Банка API поддерживает gRPC, gRPC-Web, REST-прокси и WebSocket. Основной endpoint production — `invest-public-api.tbank.ru:443`, тестовый — `sandbox-invest-public-api.tbank.ru:443`.

Основные сервисы, которые понадобятся проекту:

| Область | Сервис / методы | Применение |
|---|---|---|
| Инструменты | `InstrumentsService`: поиск инструмента, акции, фьючерсы, спецификации, расписания торгов | Каталог активов, идентификаторы, лоты, шаг цены, срок фьючерса |
| История и котировки | `MarketDataService`: `GetCandles`, `GetLastPrices`, `GetLastTrades`, `GetOrderBook`, `GetTradingStatus`, `GetTechAnalysis` | История, realtime snapshot, стакан, сделки, статус инструмента |
| Потоки рынка | `MarketDataStreamService` | Свечи, стакан, обезличенные сделки, last price и статусы |
| Заявки | `OrdersService`: `PostOrder`, `PostOrderAsync`, `GetOrders`, `GetOrderState`, `CancelOrder`, `ReplaceOrder` | Ручная и автоматическая торговля |
| Потоки заявок | `OrdersStreamService`: `OrderStateStream`, `TradesStream` | Отслеживание статуса заявок и сделок без постоянного polling |
| Счета и портфель | `UsersService`, `OperationsService`, соответствующие stream-сервисы | Баланс, позиции, доступность операций, история операций |
| Условные поручения | `StopOrdersService` | Стоп-заявки, если они поддерживаются для выбранного инструмента и режима |
| Тестирование | `SandboxService` | Проверка сценариев отправки и сопровождения заявок без реальных денег |

**Исторические свечи `GetCandles`.** Запрос принимает `from` и `to` в UTC, `instrumentId`, интервал, опциональный `limit` и тип источника свечей. В API доступны интервалы от 5 секунд до месяца, но глубина периода и максимальное количество свечей зависят от интервала и могут отличаться по инструментам.

Текущие ориентиры из документации:

| Интервал | Ориентир максимального `limit` | Глубина одного запроса |
|---|---:|---|
| 5 секунд | 2500 | до 200 минут |
| 10 секунд | 1250 | до 200 минут |
| 30 секунд | 2500 | до 20 часов |
| 1 минута | 2400 | до 1 дня |
| 2 минуты | 1200 | до 1 дня |
| 3 минуты | 750 | до 1 дня |
| 5 минут | 2400 | до недели |
| 10 минут | 1200 | до недели |
| 15 минут | 2400 | до 3 недель |
| 30 минут | 1200 | до 3 недель |
| 1 час | 2400 | до 3 месяцев |
| 2 часа | 2400 | до 3 месяцев |
| 4 часа | 700 | до 3 месяцев |
| 1 день | 2400 | до 6 лет |
| 1 неделя | 300 | до 5 лет |
| 1 месяц | 120 | до 10 лет |

Для секундных свечей доступна только история примерно за последний месяц. Данные о первой доступной минутной и дневной свече можно получить из методов сервиса инструментов (`first_1min_candle_date`, `first_1day_candle_date`). Не предполагать, что история всех инструментов начинается в одну дату.

**Архив истории.** T‑Банк также описывает отдельный REST-метод `GET https://invest-public-api.tbank.ru/history-data` для ZIP-архивов минутных свечей за год. Запрос выполняется с Bearer-токеном и `instrument_id` (либо устаревшим `figi`) и `year`. Архивы обновляются раз в день, обычно ночью; текущего торгового дня в архиве ещё нет. Внутри присутствуют идентификатор инструмента, UTC-время, OHLC и объём в лотах. Это удобно для первичной загрузки и дозаполнения истории, но текущую сессию нужно получать отдельно.

### 2.2. MOEX ISS

MOEX ISS — HTTP API, предоставляющий данные рынков Московской биржи: структуру торговых движков и рынков, режимы торгов, инструменты, описания, свечи, обезличенные сделки, котировки и исторические результаты.

Практическая роль MOEX ISS в проекте:

- независимый источник биржевых данных для истории и сверки с брокерскими данными;
- получение справочников `engine / market / board / security`;
- загрузка данных по инструментам, которые неудобно или невозможно полностью покрыть через брокерскую историю;
- подготовка собственных исторических выборок для исследований и бэктестинга.

В документации MOEX отмечено, что часть рыночной информации без подписки доступна с задержкой; realtime-доступ и отдельные наборы исторических данных зависят от подписки и условий предоставления данных. В developer manual ISS отдельно указано, что исторические данные в пространстве `/iss/history` (кроме индексов) доступны подписчикам, а анонимный доступ к текущим данным обычно имеет задержку 15 минут; стакан также может требовать подписки. Эти условия нужно проверить по текущему договору и конкретному market/board перед проектированием загрузки. Не строить стратегию, требующую актуальной котировки, на бесплатном delayed feed.

Общая форма запросов — REST/HTTP с JSON-ответом. Интроспекцию нужно делать от общего к частному:

```text
https://iss.moex.com/iss/engines.json
https://iss.moex.com/iss/engines/{engine}/markets.json
https://iss.moex.com/iss/engines/{engine}/markets/{market}/boards.json
https://iss.moex.com/iss/engines/{engine}/markets/{market}/boards/{board}/securities/{SECID}.json
```

Исторические выборки и свечи запрашивать по соответствующему пространству `/iss/history` и/или объекту `/candles` согласно интерактивному справочнику ISS для конкретного рынка. В запросах использовать период `from` / `till`, а также пагинацию `start`. Важно читать список `columns` из каждого блока ответа, а не полагаться на фиксированный порядок полей в JSON-массиве.

У MOEX инструмент не должен идентифицироваться только тикером. Нужен контекст торгового режима: как минимум `engine`, `market`, `board`, `SECID`.

### 2.3. SDK `invest-js`: что использовать

Ссылка пользователя ведёт на новый репозиторий T‑Банка `invest-js`. Важно не перепутать его со старым пакетом `@tinkoff/invest-js`, который опубликован давно и имеет другую API-модель.

В актуальной линейке пакетов `@ttech-pub/*` на дату исследования присутствуют:

| Пакет | Назначение | Рекомендация |
|---|---|---|
| `@ttech-pub/invest-sdk-node` | Высокоуровневый SDK для Node.js | **Основной выбор для backend и worker-процессов** |
| `@ttech-pub/invest-sdk-web` | SDK для браузера через gRPC-Web | Только для безопасных read-only сценариев; торговые операции лучше проксировать через backend |
| `@ttech-pub/invest-core` | Общая доменная логика, `Decimal`, конвертеры цен и общие типы | Использовать при расчётах денежных и ценовых величин |
| `@ttech-pub/grpc-node-client` | Низкоуровневый gRPC Node.js-клиент | Нужен, если требуется доступ ниже уровня команд SDK или middleware |
| `@ttech-pub/grpc-web-client` | Низкоуровневый gRPC-Web-клиент | Для браузерной интеграции на низком уровне |
| `@ttech-pub/invest-rest-client` | HTTP/JSON REST-клиент | Альтернатива gRPC там, где REST удобнее или доступнее |
| `@ttech-pub/invest-engine-node` | Движок стратегий и бэктестинга для Node.js | Оценить и протестировать до решения: использовать целиком или только отдельные компоненты |

На дату исследования опубликованные страницы npm показывают версию `1.61.0` для пакетов этой линейки; это снимок на 8 ноября 2026 г., а не обещание, что версия останется последней к моменту установки. Перед разработкой проверить `npm view` и release notes, после чего зафиксировать согласованные версии. Новая SDK-линейка ориентирована на TypeScript: команды с типизированными входами/выходами, RxJS `Observable` для stream-подписок и `Decimal` вместо вычислений цен в обычном `number`. В документации пакета для web-варианта есть примеры команд `GetSharesCommand`, `GetCandlesCommand`, `GetOrderBookCommand`, `GetMarketdataStreamCommand`, `CreateOrderCommand` и `GetPositionsCommand`; Node.js-вариант предназначен для серверного использования и дополнительно содержит поддержку sandbox и сертификатов УЦ Минцифры.

**Рекомендуемая стратегия интеграции:** обернуть SDK собственным интерфейсом `BrokerGateway`. Не использовать T‑Bank классы напрямую в стратегиях, UI и таблицах базы данных. Тогда переход на новую версию SDK или другого брокера не затронет доменную модель приложения.

Пример установки (сверить peer dependencies и совместимость версий по README выбранного релиза):

```bash
pnpm add @ttech-pub/invest-sdk-node @ttech-pub/invest-core
```

Если выбранная версия Node SDK требует отдельный transport package, установить согласованную версию `@ttech-pub/grpc-node-client`. Все пакеты `@ttech-pub/*` фиксировать одной совместимой версией, lock-файл хранить в Git. Не обновлять SDK автоматически без регрессионных тестов.

**Ключевые выводы по выбору SDK:**

- Для сервера брать `invest-sdk-node`, а не web-клиент.
- Не класть full-access токен в React/Vite bundle, `VITE_*`, localStorage или браузерные переменные.
- `Decimal` использовать на всём финансовом пути: котировка → расчёт размера позиции → округление по шагу цены → заявка → PnL.
- `invest-engine-node` рассматривать как готовый модуль-кандидат. До принятия проверить: какие типы данных он ожидает, как реализованы комиссии/проскальзывание/частичные исполнения, как сериализуются версии стратегий и поддерживается ли воспроизводимый replay. Наличие названия «backtesting engine» само по себе не гарантирует корректный для MOEX учёт фьючерсов, сессий и брокерских комиссий.

## 3. Предлагаемая архитектура

Начинать с **модульного монолита на TypeScript**, а не с десятка микросервисов. Разделить процессы по назначению и оставить общие доменные пакеты. При росте нагрузки отдельные worker-процессы можно вынести независимо.

```text
┌─────────────────────────────────────────────────────────┐
│                    React Web UI                         │
│ watchlists · charts · signals · orders · portfolio      │
└───────────────────────────┬─────────────────────────────┘
                            │ REST + WebSocket/SSE
┌───────────────────────────▼─────────────────────────────┐
│                Backend API (Fastify/Nest)                │
│ auth · query API · command API · user settings           │
└─────────┬────────────────┬───────────────────┬───────────┘
          │                │                   │
┌─────────▼──────┐ ┌───────▼────────┐ ┌────────▼─────────┐
│ Market Data    │ │ Strategy       │ │ Execution        │
│ collector      │ │ worker         │ │ worker           │
│ T-Invest       │ │ indicators     │ │ risk checks      │
│ MOEX ISS       │ │ signals        │ │ order lifecycle  │
└─────────┬──────┘ └───────┬────────┘ └────────┬─────────┘
          │                │                   │
          └────────────────┼───────────────────┘
                           │
               ┌───────────▼───────────┐
               │ Persistence & Events  │
               │ PostgreSQL/Timescale  │
               │ Redis (optional)      │
               │ raw files / Parquet   │
               └───────────────────────┘

External providers:
  T-Invest API  ← market data, account, orders, streams
  MOEX ISS      ← exchange metadata, history, verification
```

### 3.1. Компоненты

**Frontend — React + TypeScript.** Экран наблюдения за рынком, графики, список инструментов, лента сигналов, форма ручной заявки, позиции, активные поручения, журнал сделок и состояние автоторговли. Frontend не должен иметь прямого доступа к full-access API-токену.

**Backend API — Fastify или NestJS.** Авторизация пользователя, REST endpoints для UI, трансляция обновлений через WebSocket/SSE, управление настройками стратегий и торговыми режимами. Для небольшого проекта Fastify проще; NestJS удобен, если требуется строгая модульная структура и DI.

**Market Data Worker.** Историческая загрузка, realtime-подписки, проверка пропусков, нормализация, дедупликация и сохранение данных.

**Strategy Worker.** Пересчёт индикаторов, обработка закрытых свечей/рыночных событий, запуск стратегий и создание сигналов.

**Execution Worker.** Единственная часть системы, имеющая право отправлять реальные заявки. Проверяет риски и торговые ограничения, отправляет поручение, отслеживает его статус и синхронизирует сделки.

**Хранилище.**

- PostgreSQL + TimescaleDB — инструменты, свечи, сигналы, заявки, сделки, позиции, настройки, результаты бэктестинга. На старте допустим обычный PostgreSQL с партиционированием по времени.
- Redis — кэш последних котировок, блокировки, очереди задач (например, BullMQ), краткоживущие состояния stream-соединений. В MVP можно начать без Redis.
- Объектное хранилище (MinIO/S3) или файловое хранилище с Parquet — опционально для raw-архивов, крупных trade/orderbook-серий и датасетов бэктестинга.

### 3.2. Пример структуры monorepo

```text

  worker-market-data/     # загрузка истории и streaming
```

## 4. Доменная модель и идентификаторы инструментов

Это один из самых важных разделов. Типовая ошибка — использовать только `ticker` и считать его глобально уникальным.

### 4.1. Нормализованный инструмент

Создать собственную сущность `Instrument`, не равную структуре конкретного API:

```ts
export type Instrument = {
  id: string;                    // внутренний стабильный UUID
  assetType: 'share' | 'bond' | 'etf' | 'future' | 'currency' | 'index';
  ticker: string;
  name: string;
  exchange: 'MOEX';
  currency?: string;
  lotSize: number;
  minPriceIncrement: string;     // Decimal string
  priceType: 'currency' | 'point';
  brokerUid?: string;            // T-Invest instrument_uid
  brokerPositionUid?: string;
  figi?: string;                 // только совместимость / legacy
  isin?: string;
  moexEngine?: string;
  moexMarket?: string;
  moexBoard?: string;
  moexSecid?: string;
  tradingStatus?: string;
  expirationDate?: string;       // для срочных инструментов
  underlyingInstrumentId?: string;
  contractValue?: string;        // хранить как Decimal string
  metadata: Record<string, unknown>;
};
```

T‑Банк рекомендует использовать `uid`; FIGI отмечен как устаревающий идентификатор. Комбинация `ticker + class_code` важна для определения торговой позиции в API Т‑Банка. В MOEX ISS существенны `engine`, `market`, `board`, `SECID`. Хранить все идентификаторы отдельно и связывать через таблицу `instrument_provider_ids`.

### 4.2. Таблицы каталога

`instruments` — внутренняя сущность инструмента.  
`instrument_provider_ids` — соответствия `provider`, `provider_instrument_id`, `class_code`, `board`, `market`, `engine`.  
`instrument_specs` — история спецификаций с `valid_from` / `valid_to`: lot size, tick size, currency, multiplier, futures price type.  
`trading_sessions` — торговые сессии и календарь для рынка/инструмента.

Не перезаписывать спецификацию без истории. Лотность, шаг цены, параметры фьючерса и торговые статусы могут меняться; исторические расчёты должны использовать параметры, актуальные на дату сделки.

### 4.3. Особенности фьючерсов

Для фьючерсного контракта дополнительно хранить:

- уникальный UID конкретного контракта и код серии (`ticker + class_code`, для T‑Invest class_code обычно `SPBFUT`);
- базовый актив (`basic_asset` / `basic_asset_position_uid` в модели T‑Банка);
- категорию базового актива: `commodity` | `equity_index` | `currency` | `share` | `other`;
- дату экспирации и дату последнего обращения;
- границы доступной истории (`first_1min_candle_date`, `first_1day_candle_date`);
- цену в пунктах или валюте расчёта (`priceType`);
- стоимость пункта / контрактный мультипликатор (`minPriceIncrementAmount`);
- размер лота и требования по гарантийному обеспечению, если они предоставляются;
- открытый интерес, если он доступен в потоке;
- правила перехода на следующий контракт (roll schedule).

`Indicatives` (например индекс IMOEX) — отдельные неисполняемые ряды базового актива. Их свечи нельзя подменять историей фьючерсного контракта. Историю commodity/index futures загружать по `instrument_uid` конкретного контракта; покрытие фиксировать в coverage matrix (BL-039). Дополнительный источник свечей FORTS — MOEX AlgoPack (`boards/rfud/.../candles.json`), не блокер T‑Invest ingestion.

Не объединять разные серии фьючерсов в один временной ряд без явной roll-логики. Непрерывный back-adjusted ряд годится для отдельных видов анализа, но не является исполнимым инструментом. В заявке указывать конкретный контракт.

Для конвертации стоимости фьючерсных и облигационных цен использовать подходящие конвертеры SDK (`FuturesPriceConverter`, `BondsPriceConverter`) либо собственную реализацию, прошедшую unit-тесты на спецификациях. Нельзя предполагать, что цена фьючерса в пунктах равна денежной цене контракта.

## 5. Сбор и хранение рыночных данных

### 5.1. Наборы данных

Не пытаться собирать всё в первой итерации. Сначала нужны свечи и спецификации; далее — last price, trades и order book.

| Набор | Зачем нужен | Приоритет |
|---|---|---|
| Инструменты и спецификации | Каталог, tick size, lot size, contract specs | P0 |
| OHLCV candles | Графики, индикаторы, backtesting | P0 |
| Last price / best bid-ask | Контроль актуальности цены и исполнение | P0 |
| Trading status / schedule | Запрет торгов вне разрешённого режима | P0 |
| Портфель и позиции | Проверка размера позиции и риска | P0 для торговли |
| Trades | Анализ потока сделок, объёмов и импульса | P1 |
| Order book | Спред, ликвидность, глубина рынка | P1 |
| Open interest (фьючерсы) | Анализ срочного рынка | P1 |
| Полный tick/orderbook history | Микроструктура и точный replay | P2 |

### 5.2. Структура свечи

Нормализовать все источники в единый контракт:

```ts
export type Candle = {
  instrumentId: string;
  provider: 't-invest' | 'moex-iss';
  interval: '5s' | '10s' | '30s' | '1m' | '5m' | '15m' |
            '30m' | '1h' | '2h' | '4h' | '1d' | '1w' | '1M';
  timeStart: string;             // ISO UTC
  timeEnd: string;               // ISO UTC
  open: string;
  high: string;
  low: string;
  close: string;
  volume: string;
  volumeUnit: 'lots' | 'contracts' | 'shares' | 'unknown';
  turnover?: string;
  isClosed: boolean;
  sourceRevision?: string;
};
```

Цены и денежные суммы хранить строкой Decimal либо в точном decimal/numeric типе БД. Не использовать IEEE-754 `number` в качестве источника истины для цены и денег. Все внутренние временные метки хранить в UTC; для отображения использовать `Europe/Moscow` и учитывать реальные расписания торговых сессий.

### 5.3. Историческая загрузка

Реализовать единый интерфейс загрузчика:

```ts
interface HistoricalMarketDataProvider {
  getCandles(input: {
    instrumentId: string;
    interval: Candle['interval'];
    from: Date;
    to: Date;
  }): Promise<Candle[]>;
}
```

Реализовать два адаптера:

- `TInvestHistoricalProvider` — `GetCandles` и, где полезно, годовые архивы `history-data`.
- `MoexIssHistoricalProvider` — MOEX ISS JSON, пагинация, справочники и доступные исторические свечи.

Алгоритм начальной загрузки для каждого инструмента:

1. Получить и сохранить спецификацию и идентификаторы у обоих провайдеров.
2. Определить доступную глубину истории по конкретному интервалу.
3. Создать `history_import_job` с диапазоном дат и контрольной точкой.
4. Разбить диапазон на окна, не превышающие ограничения соответствующего API.
5. Запросить каждый диапазон с rate limiter и retry/backoff на временные ошибки.
6. Преобразовать данные в общий формат, проверить поля и нормализовать время.
7. Выполнить upsert по уникальному ключу `(instrument_id, interval, time_start, provider)`.
8. Сверить число свечей и границы периода, сохранить cursor/checkpoint.
9. Записать пропуски в `data_gaps`, а не создавать искусственные свечи с нулевым объёмом.
10. Повторно пройти небольшое окно на границе импорта, чтобы исправить неполные/поздно обновлённые данные.

Для T-Invest `GetCandles` ограничен интервалом и `limit`, поэтому историческую глубину нужно загружать циклом из непересекающихся или контролируемо перекрывающихся окон. Не запрашивать один огромный диапазон в надежде получить все записи.

Для MOEX ISS использовать `start` для пагинации, пока API возвращает записи; метаданные `columns` должны использоваться для сопоставления значений. Доступность `/iss/history` по конкретному рынку/инструменту проверить заранее — не считать, что исторические данные доступны без подписки для всех инструментов.

### 5.4. Догрузка текущего дня

Исторический ZIP-архив Т‑Банка не содержит текущий торговый день. Поэтому настроить два независимых потока:

- ночная/периодическая задача — скачивание архивов и backfill за завершённые дни;
- realtime stream — получение актуальных данных в течение сессии.

После завершения сессии сделать reconciliation: сравнить последнюю realtime-свечу с историческим источником и обновить свечу, если источник исправил данные. Не считать свечу окончательной до её закрытия; для стратегий по закрытию бара передавать `waitingClose: true` либо самостоятельно проверять интервал.

### 5.5. Валидация качества

Для каждой загрузки проверять:

- `low <= open <= high` и `low <= close <= high`;
- неотрицательный объём;
- отсутствие дубликатов по ключу;
- хронологический порядок;
- корректное соответствие timestamp торговой сессии;
- разумность гэпов и скачков относительно предыдущей свечи;
- источники и версии спецификаций;
- наличие пропусков, которые объясняются неторговым временем, и пропусков, которые требуют backfill.

Если данные из T‑Invest и MOEX ISS различаются, хранить их раздельно и вести статистику расхождений. Не смешивать значения без правила приоритета. Для backtesting выбрать один источник как канонический на уровне конкретной стратегии/датасета.

## 6. Realtime market data

### 6.1. Потоки

В первую очередь реализовать одну службу управления market-data subscriptions. Она должна централизованно управлять подписками, а не создавать по соединению на каждый экран UI.

Рекомендуемые типы подписок T‑Invest:

- свечи для выбранного набора инструментов и таймфреймов;
- обезличенные сделки;
- стакан с нужной глубиной;
- last price;
- изменение статуса инструмента.

У T‑Invest есть ограничения на число одновременных stream-соединений и подписок. В актуальной таблице лимитов указаны, в частности, лимит 300 одновременных подписок на свечи/стаканы/сделки в одном market-data stream и ограничение частоты отправки отдельных типов сообщений (для стакана и свечей — интервал порядка 100 мс на подписку). Планировать подписки с запасом, объединять инструменты в потоки и не подписываться заново при каждом рендере интерфейса.

### 6.2. Надёжность stream-соединения

Stream manager должен иметь следующие состояния:

`DISCONNECTED → CONNECTING → CONNECTED → DEGRADED → RECONNECTING`.

Обязательные функции:

- reconnect с exponential backoff и jitter;
- ping/heartbeat и контроль последнего события;
- восстановление подписок после reconnect;
- обнаружение stale data;
- запись последнего sequence/timestamp, если он доступен;
- запуск backfill после пропуска событий;
- метрики задержки, количества reconnect и числа потерянных/дублированных событий.

На стороне потребителя все события должны быть идемпотентными. Для свечей ключ — инструмент + интервал + время начала. Для сделок использовать id/номер сделки, если он предоставлен источником; если уникального идентификатора нет, использовать осторожный составной ключ и сохранять raw event.

### 6.3. Данные в интерфейсе

Показывать не только цену, но и качество данных:

- timestamp последнего обновления;
- источник цены;
- статус stream;
- флаг задержки/stale;
- текущий торговый статус;
- индикатор reconnect/data gap.

Автоматическая торговля должна быть запрещена, если критическая цена устарела, соединение потеряно, инструмент приостановлен или статус торгов неизвестен.

## 7. Аналитика и сигналы

### 7.1. Слои аналитики

Не смешивать расчёт индикаторов, интерпретацию рынка и генерацию заявки.

1. **Features:** технические признаки (returns, volatility, volume ratio, ATR, spread, open interest delta).
2. **Indicators:** SMA, EMA, RSI, MACD, ATR, Bollinger Bands, VWAP, OBV и т. д.
3. **Market context:** тренд/флэт, волатильность, ликвидность, сессия, календарные события.
4. **Strategy rules:** условия входа/выхода и отмены сценария.
5. **Signal:** объяснимое событие с направлением, ценовыми уровнями, сроком действия и причинами.
6. **Trade proposal:** предложение сделки с рассчитанным объёмом и риском.
7. **Execution:** реальное брокерское поручение, выполняемое только после риск-проверок.

### 7.2. Контракт сигнала

```ts
export type TradingSignal = {
  id: string;
  strategyId: string;
  strategyVersion: string;
  instrumentId: string;
  timeframe: string;
  direction: 'buy' | 'sell' | 'close' | 'hold';
  status: 'new' | 'accepted' | 'rejected' | 'expired' | 'executed';
  createdAt: string;
  validUntil: string;
  referencePrice: string;
  entryZone?: { min: string; max: string };
  stopLoss?: string;
  takeProfit?: string[];
  confidence?: number;          // оценка модели, не вероятность прибыли
  reasons: string[];
  features: Record<string, string | number | boolean>;
  dataQuality: 'good' | 'delayed' | 'stale' | 'incomplete';
};
```

Сигнал должен содержать **почему** он появился и **при каких условиях перестанет быть актуальным**. Сигнал не должен напрямую вызывать `PostOrder`.

### 7.3. Стартовые стратегии

Для первой версии достаточно нескольких прозрачных алгоритмов:

| Стратегия | Условие-пример | Что проверять |
|---|---|---|
| Moving average crossover | EMA(short) пересекает EMA(long) | Фильтр тренда, ложные пересечения во флэте |
| RSI mean reversion | RSI выходит из экстремальной зоны и подтверждает возврат | Не торговать против сильного тренда без фильтра |
| Breakout | Закрытие выше/ниже максимума/минимума lookback-периода | Фильтр объёма и волатильности, ложный пробой |
| Volume anomaly | Объём значительно выше rolling baseline | Сравнивать одинаковые фазы торговой сессии |
| ATR stop / trailing exit | Стоп на расстоянии k × ATR | Gap risk, tick size и исполнимость стопа |

Индикатор — это признак, а не готовая стратегия. Для каждого правила задавать таймфрейм, момент вычисления (закрытая свеча/каждое событие), фильтры, правила выхода и риск-параметры.

### 7.4. Объяснение сигнала

Для пользователя генерировать структурированное пояснение:

- какие условия сработали;
- какие фильтры прошли/не прошли;
- цена и timestamp данных, на которых построен сигнал;
- ожидаемая зона входа;
- invalidation level;
- расчётный стоп, цель и риск/прибыль;
- известные ограничения (спред, низкая ликвидность, близость экспирации, delayed data).

AI/LLM можно добавить как слой объяснения и суммаризации рыночного контекста. Не поручать LLM самостоятельно выбирать количество лотов или напрямую отправлять заявки. Критические правила риска должны быть детерминированными и тестируемыми.

## 8. Backtesting и оценка стратегии

Бэктестинг — отдельный обязательный контур. Исторические свечи не становятся корректным бэктестом автоматически.

### 8.1. Требования к симулятору

Симулятор должен учитывать:

- точное время появления сигнала и доступность данных в этот момент;
- исполнение не раньше следующего возможного торгового события;
- шаг цены и размер лота;
- bid/ask spread и проскальзывание;
- комиссии брокера/биржи и иные применимые издержки;
- частичное исполнение и отсутствие ликвидности;
- торговые сессии, аукционы, перерывы и неторговые дни;
- stop execution при гэпе через уровень;
- лимитные заявки, которые могли не исполниться, даже если свеча касалась цены;
- корректные спецификации инструмента на дату события;
- экспирацию и перекладку фьючерсов;
- корпоративные действия для акций, если они влияют на ряд.

**Не допускать look-ahead bias:** сигнал на закрытии свечи нельзя исполнить по цене закрытия этой же свечи, если в реальности цена стала известна лишь после её завершения. Для внутрисвечных стопов OHLC недостаточно, чтобы достоверно знать очередность high/low; нужен консервативный сценарий или tick/orderflow данные.

### 8.2. Метрики

Обязательные метрики результата:

- net PnL после комиссий и проскальзывания;
- максимальная просадка и длительность восстановления;
- Sharpe / Sortino (с оговоркой о частоте данных и корректности annualization);
- profit factor;
- expectancy на сделку;
- win rate и average win/loss;
- количество сделок, оборот, market exposure;
- комиссии как доля gross PnL;
- результат по инструменту, направлению, дню недели и рыночному режиму.

### 8.3. Методика тестирования

1. Разделить историю на train / validation / out-of-sample по времени.
2. Использовать walk-forward тестирование.
3. Не подбирать сотни параметров на одном и том же тестовом участке.
4. Сравнивать с простым benchmark (например, buy-and-hold или нулевая стратегия).
5. Сохранять неизменяемую версию стратегии, конфигурацию и ID датасета для каждого прогона.
6. Выполнять тест устойчивости: изменять комиссии, slippage и входные параметры в разумных пределах.
7. После исторического теста перейти к paper trading на новых данных, которые не использовались при разработке стратегии.

`@ttech-pub/invest-engine-node` стоит проверить как возможную основу движка стратегий/бэктеста. Если его симулятор не учитывает все перечисленные особенности, использовать его для индикаторов/правил или прототипа, а execution simulator реализовать самостоятельно. API T‑Банка предоставляет исторические котировки и торговые методы; методологию проверки торговой гипотезы приложение должно реализовать само.

## 9. Ручная торговля

Ручная торговля должна быть реализована раньше автоматической и стать базой для общего механизма исполнения.

### 9.1. Основной workflow

1. Пользователь выбирает инструмент из каталога.
2. UI показывает цену, время последнего обновления, bid/ask, спред, торговый статус и позиции.
3. Пользователь создаёт ордер или открывает предложение из сигнала.
4. Backend получает актуальную спецификацию, состояние счёта и текущие рыночные данные.
5. Risk Engine рассчитывает допустимый объём и валидирует заявку.
6. UI показывает preview: направление, тип, цена, количество лотов, ориентировочная сумма, стоп/риск, комиссия/оговорки.
7. Пользователь подтверждает действие явно.
8. Execution Worker отправляет заявку через T‑Invest API и сохраняет `order_id`.
9. Статус отслеживается через `OrderStateStream`/`TradesStream`, а при необходимости — через `GetOrderState` и `GetOrders`.
10. После сделки обновляются позиции, PnL и журнал исполнения.

### 9.2. Типы заявок

T‑Invest API документирует лимитную, рыночную и заявку «лучшая цена», а также time-in-force варианты `DAY`, `FILL_AND_KILL`, `FILL_OR_KILL` (с ограничениями по отдельным режимам/инструментам). Отдельный `StopOrdersService` отвечает за стоп-поручения.

Рекомендации для интерфейса:

- по умолчанию предлагать **лимитную** заявку;
- рыночную заявку помечать как потенциально опасную по проскальзыванию;
- до подтверждения показывать spread и доступную ликвидность стакана;
- не обещать исполнение стоп-цены при гэпе или недостатке встречной ликвидности;
- для фьючерсов явно отображать цену в пунктах/валюте, стоимость пункта и размер контракта.

Документация T‑Банка предупреждает, что рыночная заявка может исполниться по нескольким уровням стакана и по менее выгодной цене, если ликвидности на лучшем уровне недостаточно. Следовательно, рыночная заявка не должна считаться гарантированным исполнением по last price.

### 9.3. Order state machine

Хранить состояние заявки как собственную машину состояний:

```text
CREATED
  └─> SUBMITTING
        ├─> NEW / ACTIVE
        │     ├─> PARTIALLY_FILLED
        │     │     ├─> FILLED
        │     │     └─> CANCELLED
        │     ├─> FILLED
        │     ├─> CANCEL_PENDING ─> CANCELLED
        │     ├─> REJECTED
        │     └─> EXPIRED
        └─> UNKNOWN  # таймаут / неизвестен результат отправки
```

`UNKNOWN` принципиально важен. Если вызов `PostOrder` завершился timeout, нельзя вслепую повторять запрос — первая заявка могла быть принята. Сначала сверить `order_id`, активные заявки, состояние заявки и события stream.

Для запроса `PostOrder` генерировать уникальный UID `orderId` и хранить его до подтверждения результата. В API это поле используется для идемпотентности; максимальная длина — 36 символов. На уровне БД дополнительно обеспечить уникальность внутреннего `clientOrderId`.

## 10. Контролируемая автоматическая торговля

Автоматическое исполнение включать только после прохождения backtesting, sandbox и paper trading. Strategy Worker **не должен иметь права на отправку заявок**. Он публикует `TradeProposal`; Execution Worker принимает его и самостоятельно проводит все проверки.

### 10.1. Уровни запуска

| Режим | Что происходит | Требование |
|---|---|---|
| `RESEARCH` | История, индикаторы, сигналы | Нет брокерских заявок |
| `MANUAL` | Сигналы → предложение → подтверждение пользователем | Основной безопасный рабочий режим |
| `PAPER` | Симуляция заявок на realtime-данных | Сверка с реалистичным исполнением |
| `SANDBOX` | Отправка заявок в sandbox T‑Банка | Проверка API/order lifecycle, не качества реальной ликвидности |
| `LIVE_GUARDED` | Реальная торговля с ограниченными параметрами и контролем | Разрешённый whitelist, низкий лимит объёма, kill switch |
| `LIVE` | Автоматическое исполнение в рамках утверждённых лимитов | Только после отдельной оценки рисков и длительного paper-теста |

В production начинать с `LIVE_GUARDED`: одна стратегия, один-два инструмента, минимальный объём, лимит потерь и ручной контроль.

### 10.2. Pre-trade Risk Engine

Перед каждой заявкой проверить:

1. Глобальный `kill switch` выключен.
2. Разрешён ли live-режим для данной стратегии, счёта и инструмента.
3. Сигнал не просрочен и не исполнен ранее.
4. Рыночные данные свежие; отсутствует stale flag и активные data gaps.
5. Торговый статус инструмента позволяет операцию.
6. Текущая сессия открыта для соответствующего режима.
7. Инструмент соответствует whitelist и спецификация не устарела.
8. Цена соответствует шагу цены и допустимым ценовым границам.
9. Количество кратно лоту и не превышает лимит заявки.
10. Достаточно денег/активов/маржи; текущие позиции и активные заявки учтены.
11. Не превышены лимиты по инструменту, стратегии, счёту и дневному риску.
12. Нет другой конфликтующей заявки или открывающей операции по тому же инструменту.
13. Оценочный spread/slippage не превышает установленный порог.
14. Есть доступное соединение с брокерским API и корректная авторизация.

Пример абстрактного расчёта размера позиции:

```text
riskBudget = accountEquity × maxRiskPerTrade
lossPerLot = abs(entryPrice - stopPrice) × valuePerPricePointPerLot
             + estimatedFeesPerLot + estimatedSlippagePerLot
quantityLots = floor(riskBudget / lossPerLot)
quantityLots = min(quantityLots, maxLotsByRisk, maxLotsByExposure,
                   maxLotsByBrokerLimits)
```

Для акций и фьючерсов `valuePerPricePointPerLot` рассчитывается по спецификации конкретного инструмента. Для срочного рынка дополнительно проверять гарантийное обеспечение и риск-параметры счёта. Не использовать условную формулу стоимости контракта, одинаковую для всех фьючерсов.

### 10.3. Глобальные и локальные лимиты

Рекомендуемые параметры конфигурации (значения задать отдельно, не зашивать в код):

- max risk per trade;
- max daily loss;
- max total drawdown;
- max open positions;
- max notional / max lots per instrument;
- max orders per minute;
- max order value;
- max spread and slippage;
- min liquidity / min book depth;
- allowed trading sessions;
- allowed instruments and strategies;
- max consecutive losses;
- cooldown after rejection, disconnect or abnormal slippage.

При срабатывании критического лимита система должна прекратить открытие новых позиций, отправить уведомление и перейти в безопасный режим. Отдельно определить политику по уже открытым позициям: оставить без действий, закрывать вручную или выполнять заранее согласованный сценарий. Автоматическое закрытие при сбое может быть не менее опасным, чем отсутствие действия.

### 10.4. Sandbox: что он проверяет, а что нет

Sandbox T‑Банка — тестовый контур с виртуальными счетами и без влияния на реальные средства. Он полезен для проверки авторизации, методов, форматов заявок, обработки статусов и логики приложения.

Однако в документации есть ограничения: в sandbox не рассчитываются некоторые реальные показатели счёта, ставки риска, гарантийное обеспечение и ликвидность портфеля. Счета могут удаляться, хранятся ограниченный срок после последнего использования. Поэтому успешная работа в sandbox **не доказывает**, что стратегия прибыльна или что реальные ордера будут исполняться с тем же качеством.

Полноценный PAPER-режим на live market data обязателен отдельно от sandbox.

## 11. Лимиты API, ретраи и защита от дублирования

В актуальной документации T‑Банка есть лимиты unary-вызовов, отдельных торговых методов и stream-подписок. Примеры опубликованных лимитов: сервис котировок — до 600 unary-запросов/мин, сервис инструментов — до 200/мин, сервис ордеров — до 100/мин; для `PostOrder` указан лимит до 15 запросов/сек, для `CancelOrder` — до 300/мин, для `ReplaceOrder` — до 300/мин, для `PostOrderAsync` — до 600/мин. Фактические ограничения могут зависеть от метода, типа клиента и нагрузки; перед production перепроверить актуальную таблицу.

Реализовать:

- отдельный rate limiter на каждый класс API;
- очередь задач на исторические загрузки;
- exponential backoff с jitter для `429`, `5xx` и временных сетевых ошибок;
- circuit breaker для деградировавшего провайдера;
- ограничение числа параллельных запросов;
- приоритет realtime/исполнения над backfill;
- отдельные retry policy для read и write методов.

**Нельзя автоматически ретраить запись как обычный GET.** При timeout после `PostOrder` результат неизвестен. Сначала reconciliation по client order ID, данным активных заявок и order stream, затем решение об отправке.

## 12. Безопасность

1. Создать отдельный read-only токен для загрузчика/аналитики, если это соответствует текущим правам аккаунта.
2. Full-access токен держать только в backend execution worker. Не передавать его в frontend и не логировать.
3. Хранить секреты в secret manager или как минимум в защищённых environment variables вне репозитория.
4. Развести sandbox и production credentials, URL и конфигурации.
5. По возможности ограничить токен конкретным счётом.
6. Ограничить доступ к интерфейсу управления live trading: сильная аутентификация, аудит действий, защита от CSRF и контроль сессий.
7. Записывать каждое действие: пользователь, стратегия, входящий сигнал, risk checks, payload поручения (без токена), broker order ID, изменения статусов.
8. Сделать аварийную кнопку остановки новых заявок, а не только скрытие кнопки в UI. Kill switch должен проверяться backend-ом перед каждой отправкой.
9. Периодически проверять актуальность сертификатов и сетевых требований T‑Банка. В документации отдельно упоминается необходимость сертификатов УЦ Минцифры РФ для некоторых конфигураций подключения.
10. Защитить резервные копии БД и секреты; ограничить доступ к логам и выгрузкам портфеля.

## 13. Интерфейс приложения

### 13.1. Основные разделы

**1. Dashboard** — индекс/инструменты watchlist, состояние рынка, PnL, риск-показатели, последние сигналы, статус источников данных.

## 17. Эксплуатация и мониторинг

Минимальные метрики:

- API request count, latency, error rate и rate-limit events;
- stream connected/disconnected, reconnect count, last event age;
- количество подписок, candles/trades/books per second;
- import lag, jobs failed, data gaps, candle duplicates;
- signal count, rejected/expired signals;
- order submit latency, time-to-ack, partial fills, rejects, unknown order states;
- realized/unrealized PnL, daily loss, exposure, margin;
- worker health, DB connections, queue depth.

Логи структурированные JSON с `correlationId`, `instrumentId`, `strategyId`, `signalId`, `clientOrderId`, `brokerOrderId`. Не записывать токены, секреты и полные приватные заголовки.

Критические оповещения: недоступен broker API, stream потерян, превышен дневной риск, неизвестное состояние реальной заявки, расхождение локального и брокерского портфеля, массовые ошибки данных.

Для live-режима предусмотреть ежедневную reconciliation:

1. запросить активные заявки;
2. сверить статусы локальных заявок;
3. загрузить сделки и операции;
4. сверить позиции и остатки;
5. обнаружить неизвестные/потерянные события;
6. зафиксировать расхождения и запретить новые входы до разрешения критических несоответствий.

## 18. MVP: что сделать в первой версии

Не нужно сразу строить универсальную платформу. Оптимальный MVP:

1. Каталог MOEX-инструментов: акции + несколько выбранных фьючерсов.
2. T‑Invest API adapter и MOEX ISS adapter.
3. Загрузка исторических дневных и минутных свечей.
4. PostgreSQL-хранилище и контроль качества данных.
5. Текущая цена, статус торгов и stream-подписка.
6. График инструмента и базовые индикаторы.
7. 2 простые стратегии и объяснимые сигналы.
8. Backtest с комиссиями и проскальзыванием.
9. Ручная заявка с preview и подтверждением в sandbox.
10. Журнал заявок, сделок и результатов.

**Автоторговлю в MVP не включать.** Сначала доказать качество исторических данных и корректность ручного order lifecycle. Далее добавить PAPER и sandbox. Live automation — отдельный этап с самостоятельной приёмкой.

### Проверочное задание для MVP

Сделать сквозной сценарий:

- выбрать один ликвидный инструмент MOEX и один фьючерс;
- загрузить минимум 12 месяцев дневных свечей и доступную минутную историю;
- построить график, EMA(20), EMA(50), RSI(14), ATR(14);
- сформировать сигнал на пересечении EMA с фильтром RSI/ATR;
- прогнать стратегию на истории с комиссиями и slippage;
- при появлении нового сигнала в realtime создать trade proposal;
- в UI показать объяснение, рассчитанный объём и риск;
- вручную подтвердить тестовую заявку в sandbox;
- отследить статус и сохранить результат в журнале.

Результат такого задания проверяет большинство архитектурных узлов и может стать демонстрационным сценарием проекта.

## 22. Итоговая рекомендация

Для первой рабочей версии оптимальна следующая связка:

- **TypeScript / Node.js backend** — бизнес-логика и все брокерские операции.
- **`@ttech-pub/invest-sdk-node` + `@ttech-pub/invest-core`** — основной клиент T‑Invest API и точные расчёты.
- **MOEX ISS adapter** — дополнительная история, биржевая структура и независимая сверка данных.
- **PostgreSQL/TimescaleDB** — каталог, свечи, сигналы, заявки, сделки, позиции и backtest results.
- **React UI** — market watch, графики, аналитика, сигналы, ручная торговля и мониторинг.
- **Отдельные Strategy и Execution Workers** — стратегия только создаёт предложение, execution отдельно валидирует риск и отправляет поручение.

Рекомендуемый порядок: **история и каталог → realtime → аналитика и сигналы → backtesting → ручная торговля → paper/sandbox → ограниченный live**. Не начинать с автоматической торговли. Качественные данные, правильные спецификации инструментов и воспроизводимый order lifecycle важнее количества индикаторов и сложности стратегии.
